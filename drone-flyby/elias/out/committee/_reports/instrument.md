## proposals
### 1. Fix flypaste labels and class ids before anyone trains or fine-tunes on flypaste v3
- mechanism: The tile labels are the tight sprite card, not the organiser box, and the class ids are alphabetical while every repo checkpoint uses dtos.OBJECT_CLASSES order. rescale_labels.py writes a corrected copy: labels grown about their centre by per-class factors (label_factors.json), ids remapped to the repo order, data.yaml written. The exact fix is on Oscar's side: look the view up in views.json and pass its box_in_sprite instead of [0, 0, view.shape[1], view.shape[0]] to apply_perturbation (paste_sets.py line 67, paste_v3.py line 62), then python3 paste_sets.py --sets train and re-export tiles.
- evidence: views-ref-v2/views.json box_in_sprite / size_px: jet 1.48 x 1.45, condor 1.46 x 1.55, medium_launcher 1.62 x 1.45, small_launcher 1.24 x 1.58 (results/card_vs_organiser_box.txt); F3, F5 and HEL answer the same factors on the tiles (results/label_factors.txt) and 0.99 to 1.04 on the real Helsinki frames; F3 model.names order differs from the manifest class list (checked).
- expected gain: No gain by itself; it prevents a loss. A detector trained on the card labels answers boxes at IoU 0.43 to 0.51 against the organiser box on jet_plane (0.97 now), condor, medium_launcher, small_launcher and 0.66 to 0.71 on large_launcher and tank even when perfectly centred, and with the ids as they are every class is answered under another name. For any flypaste-trained candidate this is the difference between about 0 and its real score (guess: protects 0.1 to 0.5 of portal score for such a candidate).
- cost: 1 minute CPU, no GPU | gpu False portal False pod False
- risk: The factor correction is an approximation (symmetric growth, heading-averaged; small_launcher and ta-ta margins are anisotropic and hangar is not). Exact boxes need Oscar's regeneration. Never run it with --set val or both for training data (validation pixels).
- how to run: cd "C:/Users/edlun/Desktop/lucky shots/NordicCupAI-drone/drone-flyby" && "$HOME/venvs/nordic-drone/Scripts/python.exe" elias/out/committee/instrument/rescale_labels.py --set train --link-images --out "C:/Users/edlun/Desktop/lucky shots/drone-data/derived"   (smoke-tested: 15780 labels written, 14304 grown; picture orgbox_check.jpg; the images folder is a directory junction, remove it only with: cmd //c rmdir images, never rm -rf). Factors are recomputed with elias/out/committee/instrument/label_factors.py.

### 2. Gate every candidate checkpoint with benchmark.py before it gets a portal run (a gate, not a ranking)
- mechanism: Two minute detector-level check with the serving preprocessing: (a) real Helsinki views with organiser boxes must read AP 1.0 and answer/box 0.95 to 1.05 on all 16 classes, which exposes a wrong box convention or swapped class ids at once; (b) no class significantly below F3 on flypaste-val L1 and flypaste-train L1 (organiser-size labels); (c) any claimed gain must clear the paired bootstrap interval (about +-0.03 to +-0.06 per class).
- evidence: All four released checkpoints pass (a) at 1.000 with ratio 0.99 to 1.04; the benchmark separates HEL from F3 by 0.24 macro and helicopter 0.18 against 0.96, so it sees large recognition regressions; it does NOT reproduce the portal's F3 vs F5 per-class verdicts (0 of 4 at L1), so a pass is permission to spend a portal run, never a ranking.
- expected gain: 0 direct; saves portal slots (one queued attempt per team, two minutes each) and protects the single evaluation attempt from a broken checkpoint. Indirect value about one avoided bad decision.
- cost: 2 to 4 minutes wall per checkpoint including the GPU lock (56 s of GPU for val + train, about 55 to 110 s more for the real Helsinki and validation views) | gpu True portal False pod False
- risk: Misread as a ranking. Sprite leakage: F3, F5 and PSEUDO have seen both sprite pools, so their tile numbers are seen objects on unseen backgrounds. Detector level only: births, the pair rule and forecast drift are not in it.
- how to run: cd "C:/Users/edlun/Desktop/lucky shots/NordicCupAI-drone/drone-flyby"; P="$HOME/venvs/nordic-drone/Scripts/python.exe"; "$P" elias/out/committee/instrument/benchmark.py --weights CAND.pt --tag CAND   (default sets val train helsinki, zooms 1 2 0; takes and releases gpu.lock itself); "$P" elias/out/committee/instrument/benchmark.py --tag CAND --score-only --sets val train --zooms 1 2 --org-labels; "$P" elias/out/committee/instrument/compare.py F3_org CAND_org; "$P" elias/out/committee/instrument/bootstrap.py F3 CAND --set val --zoom 1. Options: --by track, --box-scale '{"medium_launcher": 0.85}', --mode single --limit 300 (seam check), --sets validation (team labels).

### 3. Judge candidates trained WITHOUT validation pixels on flypaste-val against helsinki_only, as the unseen-instance estimate for the evaluation flight
- mechanism: The portal validation cannot tell whether a model generalises to new object instances, because F3 and F5 trained on that flight's sprites and backgrounds. flypaste-val is validation sprites on unseen backgrounds, so for a model that never saw validation pixels (Helsinki sprites plus corrected flypaste-train, for example) it is clean on both counts. Baseline: helsinki_only_m1280.pt.
- evidence: HEL on flypaste-val L1: macro 0.542 (0.591 with organiser-size labels); helicopter 0.18, medium_launcher 0.13, large_tower 0.42, large_launcher 0.52, medium_plane 0.59, mine_roller 0.65. HEL's portal total on the same (unseen to it) flight is 0.601 against 0.694 for F3. HEL loses its own Helsinki helicopter when re-pasted (train L1 AP 0.06), F3 keeps 0.80.
- expected gain: On the portal validation probably nothing (F3 has seen that flight). On the evaluation flight a guess: if its objects are new instances as the validation ones were against Helsinki, a candidate that lifts helicopter, large_tower and the launchers on this test is worth one or two classes, +0.05 to +0.15; if the instances repeat, 0.
- cost: 1 to 2 minutes GPU per candidate; the training of such a candidate is another member's proposal | gpu True portal False pod False
- risk: A candidate chosen on this test may score below the routed F3 on the portal validation (memorised flight), so the two instruments will disagree and the owner must decide which flight the attempt resembles. Val sprite pool has label noise (large-launcher-c2 is probably a mine_roller).
- how to run: "$HOME/venvs/nordic-drone/Scripts/python.exe" elias/out/committee/instrument/benchmark.py --weights CAND.pt --tag CAND --sets val --zooms 1 2 --by track; then compare.py HEL CAND ap30 and bootstrap.py HEL CAND --set val --zoom 1 (preds/HEL.json is cached).

- mechanism: elias/ensemble.py already takes a separate routing table for resolution level 2. On native-resolution tiles F5 is the better detector on most classes.
- evidence: val tiles L2, F5 minus F3 with 95 % interval: macro +0.042 [+0.030,+0.052]; large_tower +0.177 [+0.136,+0.218], small_launcher +0.243 [+0.181,+0.295], medium_plane +0.066, tank +0.046, small_tower +0.033; F3 better on jet_plane -0.068, mine_roller -0.049, helicopter -0.022 (results/bootstrap_F3_F5_val_L2.txt).
- expected gain: 0 under the served L1 sweep (no L2 views are requested). With an L2 policy: unknown, and the tile benchmark disagreed with the portal at L1, so treat as a hypothesis for a one-class portal check only.
- cost: 0 to set; one portal one-class run per class to confirm | gpu False portal True pod True
- risk: Zoom-on-cue policies were rejected on the harness; this only matters if another member's policy proposal survives.
- how to run: ELIAS_ROUTE_L2='{"large_tower":1,"small_launcher":1,"medium_plane":1,"tank":1,"small_tower":1,"ta-ta":1, every other class 0}' next to the existing ELIAS_ROUTE in elias/pod_start_final.sh (list every class).

### 5. Same-day one-class portal runs of small_tower and tank, F3 against F5, then route both to F5 if they hold
- mechanism: The portal advantage of F5 on these two classes (0.89 vs 0.80, 0.93 vs 0.87) was measured against a night run of F3, not a same-day one. The tiles say F5 is never worse on either class.
- evidence: val tiles: small_tower L1 +0.012 [+0.001,+0.036], L2 +0.033 [+0.022,+0.052]; tank L1 +0.001 [-0.012,+0.008], L2 +0.046 [+0.029,+0.072]. Checklist says these runs were queued in measure_pod4.sh; results unknown to me.
- expected gain: +0.005 to +0.012 on the portal total if both differences hold (0.06 and 0.09 of one thirteenth each); 0 if they were day-to-day drift.
- cost: 4 portal one-class runs, about 10 minutes of portal time on the serving pod | gpu False portal True pod True
- risk: Small effect inside the portal's 0.01 to 0.02 run-to-run noise; only worth it if the serving pod is up anyway before the 12:00 freeze.

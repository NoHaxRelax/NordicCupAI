# boxes

## measured facts
- FLYPASTE-V3 LABELS ARE NOT ORGANISER BOXES. The README (datasets/README-flypaste.md) and every manifest.json record claim "organiser-style loose boxes projected from the sprite boxes". The code says otherwise: paste_sets.py and paste_v3.py both call apply_perturbation(view, [0, 0, view.shape[1], view.shape[0]], prm, 1.0), and apply_perturbation (drone/grid_training/synthetic_sprites.py) computes the organiser margin as (the box it is handed) minus (the sprite alpha extent). Handed the sprite canvas rect, that margin is the 3 px padding of the cut-out, so the emitted label is the silhouette box. The organiser box lives in views-*-v2/views.json as box_in_sprite and is never passed. Evidence: the two call sites, the margin lines of apply_perturbation, and the label-size table (flypaste median label width matches the cut-out canvas width, not the organiser box width: condor 111 px label against a 172 px organiser box, jet_plane 57 against 79, medium_launcher 29 against 47).
- HOW LOOSE THE ORGANISER BOX IS, PER CLASS (organiser box over silhouette box, 198 reference cut-outs, file elias/out/committee/boxes/convention.json, script convention.py): jet_plane 1.48 x 1.45, medium_launcher 1.62 x 1.45, condor 1.46 x 1.55, small_launcher 1.24 x 1.58, large_launcher 1.18 x 1.28, tank 1.16 x 1.21, small_tower 1.08 x 1.14, hangar 1.01 x 1.17, small_plane 1.04 x 1.01, helicopter 1.03 x 1.03, medium_plane 0.99 x 1.02, large_tower 0.98 x 1.00, mine_roller 0.96 x 0.98, spacecraft 0.94 x 1.00, jammer 0.91 x 0.94, ta-ta 0.97 x 0.78. Ten of sixteen classes are off by more than 10 % on at least one axis, so a detector trained on flypaste-v3 as delivered would learn the wrong convention.
- METHOD (elias/out/committee/boxes/probe_boxes.py). Oscar's tiles are 256 px crops of a 4K frame carrying one zoom level's detail but stored at source scale. The script resizes each tile to 256/f delivered px (f = 4, 2, 1 at L0, L1, L2), packs them edge to edge into a 960x540 canvas (15x8, 7x4, 3x2) and calls model.predict(canvas, imgsz=1280, conf=0.05, half=True, augment=False), the exact serving call of elias/ensemble.py, so object pixel size and the 4/3 network upsample match serving to the pixel. Detections are mapped back to the tile holding their centre and to source pixels, the unit tracking/size-prior.json and the organiser annotations use. Run on F3 = elias/release/both_m1280.pt: 14994 train tiles / 1054 canvases / 12460 detections, 14193 val tiles / 998 canvases. One GPU lock acquisition of about 6 minutes, released.
- ORGANISER BOX RECONSTRUCTED PER INSTANCE (rebox.py). organiser_w/label_w = (a*Bw + b*Bh)/(a*Cw + b*Ch) with a = |cos t|, b = |sin t|, Cw,Ch the cut-out canvas (views.json size_px, verified equal to the alpha extent plus 3 px per side on the reference PNGs), Bw,Bh the box_in_sprite extent, t the paste angle (runs/paste/<set>/<flight>/plan/placements.json). That is exactly the margin transform apply_perturbation applies, and the paste's single scale factor cancels. The recovered per-class factors match the independent pool statistics of convention.json: condor 1.51 against 1.46/1.55, jet_plane 1.47 against 1.48/1.45, medium_launcher 1.58 against 1.62/1.45, small_launcher 1.40 against 1.24/1.58, ta-ta 0.88 against 0.97/0.78.
- AGAINST ORGANISER-CONVENTION BOXES, F3'S BOX NEEDS NO SCALING. Median predicted/label width and height at L1 (the band we serve), reference pool, conf >= 0.25 (table_train_org.txt): condor 1.00/0.97, hangar 0.95/0.97, helicopter 1.17/1.14, jammer 0.91/0.91, jet_plane 0.96/0.96, large_launcher 0.97/1.04, large_tower 1.00/1.02, medium_launcher 1.12/0.93, medium_plane 0.92/0.93, mine_roller 0.98/0.99, small_launcher 0.97/0.81, small_plane 0.96/0.97, small_tower 0.94/0.96, spacecraft 0.96/0.96, ta-ta 0.97/0.96, tank 0.96/0.96. Centre offsets are within 0.03 of the label side everywhere except large_launcher dy -0.12 and small_tower dy -0.05. Median IoU when found is 0.72 to 0.93.
- PER-CLASS OPTIMUM AGAINST ORGANISER TRUTH: searching (sw, sh) on a 0.02 grid from 0.50 to 1.70 to maximise the share of labels reaching IoU 0.50, ten of sixteen classes have their optimum exactly at (1.00, 1.00) and NO class gains more than +0.022 under the served extent policy (table_train_org.txt). The classes that score badly (large_tower 0.34, medium_launcher 0.19, small_launcher 0.25, ta-ta 0.41, helicopter 0.41 at L1) fail on detection recall, not on box geometry: their median IoU when found is 0.73 to 0.93. So the IoU 0.1 to 0.5 loss that miss_analysis.py reports is not a systematic convention error of the detector.
- THE BLEND WITH THE HELSINKI SIZE PRIOR IS WHAT COSTS BOXES. Emitted-box recall at IoU 0.50, L1+L2, conf >= 0.25 (summary.txt): macro over 16 classes on the organiser-truth pool 0.738 blend / 0.738 served config / 0.744 all-detector extents; macro over 11 classes on the validation pool 0.706 / 0.709 / 0.729. Per class the blend never wins on organiser-truth boxes. On validation objects it costs large_launcher 0.577 against 0.747 (-0.170), jet_plane -0.034, tank -0.025, small_tower -0.022, hangar -0.022, large_tower -0.007, and gains only mine_roller +0.074 against team boxes whose convention the portal contradicts (our mine_roller portal AP is 0.93). The same ordering holds at conf 0.15 and 0.05.
- THE DEPLOYED medium_launcher 0.85 IS SAFE AND IS INDEPENDENTLY REPRODUCED. Recall delta at IoU 0.50 under the served config: -0.002 on organiser-truth objects, +0.032 on validation objects (score_scale.py). The per-class optimum on the validation pool under the detector extent policy is a uniform 0.80 to 0.85, which reproduces the portal's medium_launcher 0.127 to 0.360 from a completely different measurement. 0.90 costs 0.000 on the organiser pool for the same validation gain (+0.030), so 0.85 to 0.90 is a plateau.
- OPTIMA MOSTLY DO NOT TRANSFER BETWEEN POOLS, AND THE EXCEPTIONS ARE KNOWN LABEL ARTEFACTS. Delta recall at IoU 0.50, uniform scale, train | val (sweep_uniform.json): large_launcher 0.85 gives +0.003 | +0.128 and 0.90 gives +0.019 | +0.100 (agree); medium_launcher 0.85 gives -0.002 | +0.032 (agree); helicopter 0.85 gives +0.014 | -0.123 (disagree); jet_plane 0.85 gives -0.024 | +0.055 (disagree); small_tower 1.20 gives -0.036 | +0.074 (disagree); mine_roller 1.20 gives -0.099 | -0.001 (disagree). The three classes whose validation optimum pulls the other way (jet_plane 0.82, small_tower 1.24, mine_roller 1.22) are exactly the three the checklist flags as team-label artefacts, with portal APs of 0.97, 0.80 to 0.89 and 0.93.
- PER-AXIS SCALES CANNOT BE DERIVED FROM THIS DATA. Oscar pastes every sprite at a random heading (placements.json angles cover the full circle, median 195 degrees, 100 % of frames beyond 1 degree), which mixes the two axes of the convention. The reconstructed gx and gy come out within 0.01 of each other for every class, so only uniform scales are supported here. The per-axis optima the grid search reports (for example jammer [1.02, 1.62]) are flat-plateau noise: they change recall by +0.002 or less.
- A CENTRE SHIFT WOULD BUY NOTHING. large_launcher's predicted box centre sits 0.12 of the box height above the organiser box centre at L1 and 0.11 at L2 (train pool) and 0.07 on the validation pool, a real convention difference that DRONE_BOX_SCALE cannot express. Adding a free centre shift on top of the best scale gains +0.000 for every class at every zoom (the +shift column of table_train_org.txt), because large_launcher already reaches IoU 0.50 on 92 % of organiser-truth labels.
- CONFLICT WITH CHECKLIST ROW C0c, STATED OPENLY. C0c measured blend 0.600 against detector-only 0.577 on the laptop harness. My per-detection measurement says the opposite on both object pools. The harness runs the whole pipeline against team labels and the checklist itself states the harness cannot rank box tweaks, so this is not a contradiction of evidence quality but it does mean only a one-class portal run settles the extent-policy question.
- VALIDATION-POOL CAVEAT. The val pool's box_in_sprite entries come from the team's validation tracks (views-val-v2 review_status score_positive_group_projected_track), not from organiser truth, so every val number is a statement about the team convention. I used it only to test transfer, never as truth. The organisers' boxes for validation objects are reachable only through the portal, which I did not use.

### 1. Add "large_launcher": 0.88 to DRONE_BOX_SCALE (the full proposal: {"medium_launcher": 0.85, "large_launcher": 0.88})
- mechanism: The emitted large_launcher box is the geometric mean of the detector box and the Helsinki size prior (150 x 108 source px, tracking/size-prior.json, fitted on the 25 reference frames). Measured against reconstructed organiser truth the detector's own box is already right (width ratio 0.97, height ratio 1.04), so the blend only inflates it, and on a validation-type launcher it inflates it past IoU 0.50. A uniform 0.88 about the box centre cancels the inflation. It reuses the exact switch and code path that is already portal-proven for medium_launcher (example.py _scaled).
- evidence: elias/out/committee/boxes/summary.txt and sweep_uniform.json. Recall at IoU 0.50 for the emitted box: +0.009 on organiser-truth objects (0.894 to 0.904) and +0.126 on validation objects (0.577 to 0.704). Positive on BOTH pools for every value from 0.85 to 0.95, so it is not a tuned edge. Among matched detections the conditional share crossing IoU 0.50 rises from 77 % to 94 % on the validation pool. Holds at conf 0.25, 0.15 and 0.05.
- expected gain: +0.00 to +0.015 on the portal total, most likely +0.005. Portal large_launcher AP is 0.73; if the unseen flight's launcher resembles the validation one the class gains roughly 0.10 to 0.20 AP, which is 0.008 to 0.015 of the 13-class macro; if it resembles the Helsinki one the gain is near zero. It cannot plausibly cost more than about 0.003, because the organiser-truth pool measures +0.009 recall, not a loss.
- cost: 0 to apply; about 3 minutes of portal time for one concealed one-class confirmation run | gpu False portal True pod False
- risk: Low. One class, one switch already in the deploy block, already portal-proven for another class. Residual risk: an unseen large launcher physically bigger than Helsinki's, where 0.88 would cost a little; the organiser-truth pool bounds that at -0.00 to -0.01 recall.

### 3. Stop any retrain on flypaste-v3 labels as delivered: they are silhouette boxes, one argument is wrong
- mechanism: paste_sets.py and paste_v3.py hand apply_perturbation the sprite canvas rectangle where the organiser box in sprite coordinates belongs. apply_perturbation derives the organiser margin as (given box) minus (alpha extent), so the margin collapses to the 3 px cut-out padding and the exported label is the silhouette. A detector trained on those labels learns tight boxes and gives up the loose convention the organiser truth scores.
- evidence: The two call sites (paste_sets.py and paste_v3.py, the apply_perturbation(view, [0, 0, view.shape[1], view.shape[0]], prm, 1.0) line), the margin computation inside apply_perturbation, and elias/out/committee/boxes/convention.json: the organiser box is 16 % to 62 % larger than the silhouette on at least one axis for ten of sixteen classes (jet_plane 1.48 x 1.45, medium_launcher 1.62 x 1.45, condor 1.46 x 1.55, small_launcher 1.24 x 1.58, and ta-ta the other way at 0.97 x 0.78). Independent confirmation from the detector side: F3's raw predicted/label ratio on flypaste labels equals the per-class organiser-over-silhouette factor almost exactly (condor 1.44 against 1.46, jet_plane 1.40 against 1.48, large_launcher 1.18 against 1.18, mine_roller 0.96 against 0.96, spacecraft 0.93 against 0.94), which is only possible if the labels are silhouettes and F3 already predicts the organiser convention.
- expected gain: No gain; it removes a trap. Training on these labels would reproduce a regression of the size the F5 data change caused on the portal (0.694 to 0.614), and would also corrupt any validation measurement run against these labels.
- cost: 0 to circulate the warning; regeneration is Oscar's pod work (python3 paste_sets.py --sets train both plus the tile export, a few hours) | gpu False portal False pod False
- risk: None to apply the warning. The only risk is the committee ignoring it and shipping a checkpoint trained on tight boxes.
- how to run: Tell every member whose proposal retrains or fine-tunes on flypaste-{train,both}-v3. The fix on Oscar's pod is one argument in paste_sets.py and paste_v3.py: apply_perturbation(view, f_view['box_in_sprite'], prm, 1.0) in place of apply_perturbation(view, [0, 0, view.shape[1], view.shape[0]], prm, 1.0), where f_view is that cut-out's entry in views-*-v2/views.json. Without regenerating, the exported labels can be corrected in place with the per-instance factors that elias/out/committee/boxes/rebox.py computes in about 1 second: "$HOME/venvs/nordic-drone/Scripts/python.exe" rebox.py --jsonl <probe jsonl> --manifest <dataset>/manifest.json --set train --out <corrected jsonl>

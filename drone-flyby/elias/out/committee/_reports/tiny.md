# tiny

## measured facts
- INSTRUMENT. Oscar's tiles are 256 px crops stored at 256 px whatever the zoom (manifest 'degradation': INTER_AREA to 64/128 px then INTER_LINEAR to 256), so feeding them raw to the detector is the wrong pixel scale. elias/out/committee/tiny/tile_eval.py brings each tile back to its delivered resolution (256 -> 64/128/256 for L0/L1/L2) and packs tiles into a 960x540 canvas fed at imgsz 1280 conf 0.03 half=True, the same call elias/ensemble.py makes, so object pixel sizes in the network input equal the live pipeline. build_cache.py builds the canvases once on CPU (40 to 85 s per set, cache in the session scratchpad), run_cached.py runs a checkpoint over all three zooms in 23 to 27 s. Canvases: val 40/169/789, train 42/179/833 at L0/L1/L2. Scored GT = manifest fully_contained boxes; clipped edge boxes are ignore regions; detections centred in the unused canvas margin are dropped. Evidence: elias/out/committee/tiny/smoke_z1.png (a canvas with its GT drawn), tables.txt.
- THIS DATASET CANNOT RANK OUR CHECKPOINTS. calibrate.py compares the F3-vs-F5 ranking on flypaste-val-v3 tiles with the per-class portal ranking in research/05-handover-to-oscar.md section 1 (ties under 0.02): large_launcher tiles F5 (0.644 vs 0.620) portal F3 (0.74 vs 0.58) NO; small_launcher tiles F5 (0.367 vs 0.248) portal F3 (0.34 vs 0.31) NO; tank tiles tie portal F5 NO; small_tower tiles F5 (0.898 vs 0.846) portal F5 (0.89 vs 0.80) YES; medium_plane tiles F3 portal F5 NO; medium_launcher tiles tie portal F3 NO. One agreement of six. Two causes are visible: Oscar's val sprite pool does not reproduce the flight's shapes for every class (large_launcher median 63.6x74.1 native against the flight's 120x66, width ratio 0.53) and his projected boxes are not our convention (our jet_plane boxes measure 1.31x the flypaste box while the portal scores our jet_plane 0.97). File: elias/out/committee/tiny/calibration.txt.
- COVERAGE. flypaste-val-v3 has NO ta-ta and NO small_plane sprites (Oscar's validation pool is the 11 team-label classes; datasets/stats.json 'val'->'classes'), so those two can only be measured on the reference (Helsinki) sprite, which is a different object: the reference ta-ta box is 29.4x32.3 native against the leaning validation walker's 19x33, a width ratio of 1.55. small_launcher and medium_launcher ARE covered at the right sizes: at L1 the val set puts 291 small_launcher boxes in the 8-12 delivered-px bin and 165 in 12-16 (flight value 12x15), and 283 medium_launcher in 16-24 (flight value 15x22). Source: manifests of flypaste-{train,val}-v3, scan reproduced in my session and in tables.txt; flight sizes measured from src/validation/annotations/*.json (249 files).
- SIZE RESPONSE AT THE DELIVERED SIZE THE SWEEP GIVES (size_by_zoom.txt, recall / recall at conf>=0.25). small_launcher at L1 10-13 px: F3 0.41/0.25, F5 0.43/0.21; the same object at L2 20-26 px: F3 0.59/0.35, F5 0.79/0.58. ta-ta (reference sprite) at L1 13-16 px: F3 0.69/0.52, F5 0.58/0.39; at L2 26-34 px: F3 0.81/0.67, F5 0.91/0.79. Pooled AP50 L1 -> L2: small_launcher F3 0.26 -> 0.44, F5 0.33 -> 0.67; ta-ta F3 0.57 -> 0.62, F5 0.54 -> 0.79. So four to six of every ten small launchers are not detected at any confidence at the L1 size, and a real zoom roughly doubles them.
- medium_launcher IS NOT PIXEL-STARVED; IT IS A BOX PROBLEM. It is the only class that gets WORSE at L2 (F3 AP 0.29 at L1 against 0.18 at L2; F5 0.38 against 0.16). Of 671 F3 misses on validation sprites, 173 are right class at IoU 0.1 to 0.5 and 128 are covered by a 'tank' detection (F5: 288 by tank). Its hit boxes measure 1.30 x 1.22 of the flypaste box at L1 and 1.31 x 1.23 at L2, near misses 1.31 x 1.22, median hit IoU 0.60 to 0.62 — the class sits exactly on the IoU 0.5 boundary. On reference sprites the overshoot is worse (hits 1.38 x 1.20, near misses 1.64 x 1.38). This reproduces the portal-confirmed DRONE_BOX_SCALE 0.85 story from independent pixels but does NOT calibrate the scale, because jet_plane shows the same 1.31 overshoot while scoring 0.97 on the portal. Files: tables.txt section 4, tiny_detail.py section A.
- small_launcher MISSES ARE PLAIN BLINDNESS, NOT CONFUSION OR BOXES. Of 969 F3 misses of 1440 GT, only 34 are right-class-wrong-IoU and only 30 are covered by another class's detection. Confidence separation: TP median 0.321 p10 0.055, FP median 0.075 p90 0.302 with 92 of 634 FPs at or above 0.25. medium_launcher: TP median 0.281, FP median 0.160 with 187 of 451 FPs at or above 0.25. These two are the only classes whose same-class FP distribution overlaps the TP distribution that badly. File: tables.txt sections 4 and 5.
- TEST-TIME MAGNIFICATION IS HARMFUL FOR EVERY CLASS AT EVERY SETTING. Same L1 canvases, same F3, only the network input changes. AP50 at 1280 / 1600 / 1920 / 2560 / 2x2 overlapping crops at 1280: small_launcher 0.258 / 0.130 / 0.045 / 0.039 / 0.055; medium_launcher 0.288 / 0.291 / 0.071 / 0.030 / 0.050; tank 0.941 / 0.897 / 0.527 / 0.049 / 0.384; small_tower 0.915 / 0.789 / 0.564 / 0.308 / 0.537; helicopter 0.929 / 0.889 / 0.587 / 0.264 / 0.555. F5 behaves the same at 1920 and 2560. The detector handles a real zoom (L2) well and artificial magnification not at all. This extends checklist row A4 (1536 gave 0.582 vs 0.600) with a per-class measurement on organiser-style boxes and closes both 'test-time upscaling for the tiny classes' and 'second-pass crop detector'. Files: raw_F3_val_z1_{1280,1600,1920,2560,crop2}.json, tables.txt.
- A PER-CLASS BIRTH THRESHOLD DOES NOT HELP. The tiles show the tiny classes give up much more to the single birth threshold than the big ones (L1, F3, val sprites, recall/false positives of that class): small_launcher t=0.05 0.33/247, t=0.15 0.26/81, t=0.25 0.21/42; medium_launcher 0.44/128, 0.35/91, 0.29/81; tank 0.96/84, 0.92/37, 0.89/27; ta-ta (reference) 0.54/14, 0.46/3, 0.41/1. I built elias/out/committee/tiny/classboost.py, a detector wrapper that gives a class its own birth/update pair through a monotone piecewise-linear confidence remap (so the class's own ranking and AP are untouched and only the birth decision changes), usable as --detector elias.out.committee.tiny.classboost:build with TINY_BIRTH. Four harness runs, F3, DRONE_CLUSTER_BIRTHS=1, DRONE_BOX_SCALE {"medium_launcher": 0.85}, imgsz 1280, conf 0.05: baseline 0.685; small_launcher+medium_launcher birth 0.12 -> 0.681 (small_launcher 0.573 to 0.538); small_launcher birth 0.18 -> 0.681 (0.573 to 0.536); medium_plane+small_tower+tank+medium_launcher birth 0.15 -> 0.684 (medium_plane 0.941 to 0.934). Every untouched class is bit-identical across the four runs, so the wrapper is inert where it should be. File: elias/out/committee/tiny/harness_runs.txt.
- THE small_launcher ANSWER BOX IS ALREADY RIGHT. Two more harness runs on the same baseline: DRONE_BOX_SCALE {"medium_launcher": 0.85, "small_launcher": 0.85} gives small_launcher 0.573 -> 0.500 (mAP 0.678); adding small_launcher:detector to DRONE_CLASS_EXTENT gives 0.573 -> 0.542 (mAP 0.682). The Helsinki size-prior blend beats both, so the 28 % 'box' share miss_analysis.py reports for small_launcher is not fixed by a scale and the class's loss really is recall. File: harness_runs.txt (T_SLBOX85, T_SLEXT).
- ta-ta: F3 IS NOT BLIND TO THE CLASS, ONLY TO THAT INSTANCE. On reference sprites at L1, F3 scores ta-ta AP 0.57 recall 0.58 and F5 0.54 / 0.56, although the portal scores F3 exactly 0.00 and F5 0.50 on the validation walker. F5's real advantage is at L2 (0.79 against 0.62). F3's ta-ta hit boxes are 0.86 x 0.84 of the flypaste box and F5's 0.86 x 0.82, so neither emits the big shadow-inclusive box that checklist row A12 worried about. Files: tables.txt (F3_train/F5_train), tiny_detail.py section A.
- small_plane IS NOT A TINY-CLASS PROBLEM FOR OUR DETECTOR. On reference sprites at its L1 size (20-26 delivered px) F3 recall is 0.94 with 0.87 above the birth threshold, and pooled AP50 0.765 (F5 0.785). Its portal 0.66 has some other cause; I could not measure it against validation pixels because flypaste has no small_plane validation sprite, and the team pseudo-labels do not contain the class either, so the laptop harness cannot see it.
- UNSEEN-FLIGHT SANITY CHECK. helsinki_only_m1280.pt is the only checkpoint that never saw validation sprites. On flypaste-val-v3 at L1 it collapses on helicopter (AP 0.19 against F3's 0.93), large_launcher (0.38 against 0.69), large_tower (0.59 against 0.87) and small_tower (0.71 against 0.91), while tank (0.91) and medium_plane (0.53) hold. F3 and F5 have seen every sprite in both tile sets, so every absolute number in this report is optimistic and only within-checkpoint comparisons are safe. ### 3. Box-size hedging for medium_launcher and ta-ta: emit each answer box twice at two scales
- mechanism: For these two classes only, emit the answer box a second time at a different scale (for example medium_launcher at 0.85 and 0.70, ta-ta at 1.00 and 1.20) with the duplicate at confidence x 0.5. Under COCO AP the duplicate that does not match is a false positive ranked below the primary, which costs a little precision at the tail; the one that does match turns an IoU 0.3-to-0.5 near miss into a hit. It removes the need to know the exact organiser convention for the two classes where we do not know it.
- evidence: medium_launcher lives on the IoU 0.5 boundary: median hit IoU 0.60 to 0.62 with a uniform 1.2 to 1.3 box overshoot, and 173 of 671 misses on validation sprites are right class at IoU 0.1 to 0.5 (tables.txt section 4, tiny_detail.py section A). The team's own portal replay of fixed ta-ta boxes scored AP 0.74 using three box sizes (research/03-checklist.md, 'Done today'), which is the same trick, against F5's 0.50 live. The 0.85 scale already moved medium_launcher 0.127 to 0.360 on the portal, so the class responds strongly to box geometry.
- expected gain: -0.005 to +0.02 on the total. Upper end if the deployed scale is off for either class (medium_launcher 0.36 towards 0.45-0.60, ta-ta 0.50 towards 0.55-0.70); zero if both scales are already right; slightly negative only through tail precision.
- cost: about 20 minutes to write, 0 GPU; plus one concealed one-class portal run per class to verify | gpu False portal True pod True
- risk: Moderate. It cannot be ranked on the laptop harness, because the harness box convention differs from the organisers' for several classes (research/03-checklist.md, loss decomposition). Keep it behind an env switch that is off by default and do not ship it unverified.
- how to run: It belongs in the answer emission of example.py, beside the existing DRONE_BOX_SCALE handling, NOT in the detector or the tracker: I verified that a wrapper detector cannot do it, because a second overlapping same-class detection is swallowed by the ambiguous_detection rule in tracking/revisit.py (DRONE_CLUSTER_BIRTHS=1 keeps exactly that behaviour for overlapping detections). Suggested switch: DRONE_BOX_HEDGE='{"medium_launcher": [0.85, 0.70], "ta-ta": [1.0, 1.2]}' plus DRONE_BOX_HEDGE_CONF=0.5. I did not write it: rule 1 forbids me to edit repo files. Verify with one concealed one-class run per class through elias/pod_portal.sh with DRONE_ANSWER_CLASSES set, paired against the deployed config in the same hour.
